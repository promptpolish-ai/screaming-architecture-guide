Stop Packaging by Layer. Your Codebase Is Screaming for Help.

The #1 mistake I see in codebase reviews — across startups, enterprises, and open source projects — is packaging by layer instead of by feature.

If your src/ folder looks like this, keep reading:

src/
  controllers/     ← User, Order, Product, Auth controllers... all mixed
  models/          ← 47 different entities in one folder
  services/        ← Business logic from every domain, tangled together
  repositories/    ← Database queries for everything, everywhere

I've reviewed hundreds of codebases over 15 years. More than 90% fail this test. And the fix takes 10 minutes to understand and a weekend to implement.

The 10-Second Test

Open your project's src/ folder. Can you tell what the application does within 10 seconds?

If your answer is anything other than "YES, it's clearly an e-commerce platform / banking system / task manager", your architecture is failing its primary job: communication.

❌ Painful Architecture: This screams NOTHING about the domain.
✅ Screaming Architecture: This screams "I AM AN E-COMMERCE SYSTEM."

The Fix: Package by Feature

This is the single highest-impact change you'll ever make to your project structure.

Instead of scattering each feature across 4 directories, group everything about a feature in one directory:

src/
  orders/
    OrderController.ts     ← HTTP layer
    OrderService.ts        ← Business logic
    OrderRepository.ts     ← Database
    Order.ts               ← Domain entity
    OrderDTO.ts            ← Data transfer
    
  users/
    UserController.ts
    UserService.ts
    UserRepository.ts
    User.ts
    UserDTO.ts

Why this works:

  • To understand "Orders", open ONE directory
  • Adding a feature = adding ONE directory
  • Removing a feature = removing ONE directory
  • Extracting to a microservice = copying ONE directory
💡 The test: If you can't delete a complete feature by removing a single directory, your architecture has unnecessary coupling.

The Dependency Rule

Once your features are grouped, the next step is enforcing the Dependency Rule:

┌─────────────────────────────────────┐
│         Presentation (HTTP)         │
│           depends on →              │
├─────────────────────────────────────┤
│       Application (Use Cases)       │
│           depends on →              │
├─────────────────────────────────────┤
│         Domain (Entities)           │
│         ⚡ ZERO dependencies        │
└─────────────────────────────────────┘
         ↑ implements ports
┌─────────────────────────────────────┐
│      Infrastructure (DB/APIs)       │
└─────────────────────────────────────┘

The rule: Source code dependencies always point INWARD, toward the domain.

Your domain layer should have zero imports from frameworks, databases, or HTTP libraries. If your Account.ts imports Mongoose, Express, or Sequelize, you're coupled to a framework.

Use Cases as First-Class Citizens

Your application's behavior should be explicit. Name your classes so they scream intent:

// This class name screams what it does
class TransferMoneyUseCase { ... }
class CancelSubscriptionUseCase { ... }
class ApproveRefundUseCase { ... }

// Compare with:
class OrderService { ... }       ← What about orders? Create? Update? Delete?
class PaymentHandler { ... }     ← Handles what? When? Why?

When every use case is a named class with a single public method, the codebase documents itself. A new developer can understand what the system does by reading the list of use case classes.

Real Talk: The Objections

"This is overengineering for a small project."

No, it scales down. A Todo app:

src/
  todos/
    application/CreateTodoUseCase.ts
    application/CompleteTodoUseCase.ts
    domain/Todo.ts
    infrastructure/InMemoryTodoRepository.ts
    presentation/TodoController.ts

6 files. Zero overengineering. Crystal clear intent.

"My framework forces its own structure."

Frameworks serve you, not the other way around. Create a src/ layer on top following screaming principles. Let the framework layer be just another infrastructure detail.

"It takes too long to refactor."

What's more expensive: 30 minutes restructuring now, or 30 hours debugging coupled code in 6 months?

The Audit

Score your project (0 or 1 for each):

  • Can you tell what the app does looking at src/?
  • Are features in their own directories?
  • Does domain have zero framework imports?
  • Are use cases named as VerbNoun?
  • Could you swap the framework changing only one layer?
  • Does test structure mirror source structure?
